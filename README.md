## 5. MAC 연산 원리

| 단계 | 설명 |
|---|---|
| Multiply | 같은 위치의 패턴 값과 필터 값을 곱함 |
| Accumulate | 곱한 값을 모두 더함 |
| Score | 누적 합계를 해당 필터의 점수로 사용 |
| Decision | Cross 점수와 X 점수를 비교해 더 큰 쪽으로 판정 |

핵심 코드:

```python
score += pattern[i][j] * filter_[i][j]
```

예시:

| 비교 | 점수 |
|---|---:|
| 입력 패턴 vs Cross 필터 | Cross score |
| 입력 패턴 vs X 필터 | X score |

판정 규칙:

| 조건 | 결과 |
|---|---|
| `Cross score > X score` | `Cross` |
| `X score > Cross score` | `X` |
| `abs(Cross - X) < 1e-9` | `UNDECIDED` |

## 6. 라벨 정규화

`data.json`에는 같은 의미의 라벨이 서로 다르게 들어올 수 있습니다.

| 원본 라벨 | 내부 라벨 |
|---|---|
| `cross` | `Cross` |
| `+` | `Cross` |
| `x` | `X` |

정규화가 필요한 이유:

| 문제 | 설명 |
|---|---|
| 문자열 불일치 | `+`와 `Cross`는 의미는 같지만 문자열은 다름 |
| 잘못된 FAIL 방지 | 정규화 없이 비교하면 정답도 FAIL 처리될 수 있음 |
| 출력 통일 | 콘솔 결과를 `Cross` / `X` 기준으로 표시 |

## 7. 부동소수점 비교

| 항목 | 내용 |
|---|---|
| 기준값 | `EPSILON = 1e-9` |
| 비교식 | `abs(score_a - score_b) < EPSILON` |
| 동점 결과 | `UNDECIDED` |

필요한 이유:

| 예시 | 설명 |
|---|---|
| `0.9` | 수학적으로는 0.9 |
| `0.8999999999999999` | 컴퓨터 내부 표현으로 생긴 미세 오차 |
| 차이 `< 1e-9` | 사실상 같은 값으로 판단 |

## 9. 실패 원인 분석

| 케이스 | 분류 | 원인 |
|---|---|---|
| `size_5_1` | 수치 비교 문제 | 두 점수 차이가 epsilon보다 작아 `UNDECIDED` |
| `size_13_2` | 수치 비교 문제 | `7.499999999999997`과 `7.5`가 epsilon 범위 안에 있음 |
| `size_25_1` | 수치 비교 문제 | `4.9`와 `4.899999999999999`가 epsilon 범위 안에 있음 |

정리:

| 항목 | 판단 |
|---|---|
| 데이터 스키마 오류 | 아님 |
| MAC 계산 로직 오류 | 아님 |
| 라벨 정규화 오류 | 아님 |
| 부동소수점 epsilon 정책 영향 | 맞음 |

결론:

| 내용 |
|---|
| 실패 3개는 프로그램이 epsilon 규칙을 적용했기 때문에 발생 |
| expected는 한쪽 라벨을 요구하지만 실제 점수 차이는 매우 작음 |
| 과제 요구사항의 epsilon 기반 비교를 지키면 `UNDECIDED` 처리가 타당 |

### 제출용 실패 원인 분석

`data.json` 분석 결과 실패한 케이스는 `size_5_1`, `size_13_2`, `size_25_1` 세 개이다.
세 케이스 모두 입력 배열의 크기나 JSON 스키마가 잘못되어 실패한 것이 아니다.
각 케이스는 `input` 필드를 가지고 있고, 패턴 크기도 키에서 추출한 N값과 일치한다.
또한 `expected` 값도 `x` 또는 `+` 형태로 들어와 있으며, 프로그램 내부에서 `X`와 `Cross`로 정상 정규화된다.
따라서 실패 원인을 데이터 형식 문제나 라벨 정규화 문제로 보기는 어렵다.
MAC 계산 로직 역시 모든 위치의 `pattern[i][j] * filter[i][j]` 값을 더하는 방식으로 동일하게 적용된다.
정답이 명확한 `size_5_2`, `size_13_1`, `size_25_2`가 PASS된 점을 보면 기본 판정 로직도 정상적으로 동작한다.
실제 실패 원인은 부동소수점 점수 차이가 매우 작아 epsilon 동점 규칙에 걸린 것이다.
예를 들어 `size_5_1`은 Cross 점수가 `0.9`, X 점수가 `0.8999999999999999`로 출력된다.
수학적으로는 거의 같은 값이지만 컴퓨터의 이진 부동소수점 표현 때문에 마지막 자리에서 미세한 차이가 생긴다.
이 프로그램은 과제 요구사항에 따라 `abs(score_a - score_b) < 1e-9`이면 한쪽을 억지로 고르지 않고 `UNDECIDED`로 처리한다.
그 결과 expected는 `X` 또는 `Cross`인데 실제 판정은 `UNDECIDED`가 되어 FAIL로 집계된다.
즉 현재 FAIL은 프로그램이 잘못 계산해서 생긴 실패가 아니라, 허용오차 기반 비교 정책을 엄격하게 적용한 결과이다.
만약 expected와의 일치를 더 우선하려면 epsilon 값을 줄일 수 있지만, 그러면 부동소수점 오차를 안정적으로 처리한다는 목적이 약해진다.
따라서 현재 구현에서는 세 실패 케이스를 수치 비교 정책에 따른 정상적인 진단 결과로 분류한다.

## 10. 성능 분석

측정 조건:

| 항목 | 값 |
|---|---|
| 반복 횟수 | 10회 |
| 측정 단위 | ms |
| 측정 범위 | MAC 함수 호출 구간 |
| 제외 | 파일 읽기, 콘솔 출력, 사용자 입력 |

측정 예시:

| 크기 | MAC 횟수 | 평균 시간(ms) |
|---|---:|---:|
| 3x3 | 9 | 0.0122 |
| 5x5 | 25 | 0.0066 |
| 13x13 | 169 | 0.0320 |
| 25x25 | 625 | 0.0866 |

시간 복잡도:

| 항목 | 설명 |
|---|---|
| 반복 구조 | 이중 반복문 |
| 방문 칸 수 | `N * N` |
| MAC 횟수 | `N^2` |
| 시간 복잡도 | `O(N^2)` |

해석:

| 내용 |
|---|
| 배열 크기가 커질수록 처리해야 할 칸 수가 제곱으로 증가 |
| 작은 크기에서는 함수 호출과 시간 측정 오차가 상대적으로 크게 작용 |
| 13x13, 25x25에서는 MAC 횟수 증가에 따라 실행 시간도 증가 |
| 순수 Python 반복문이므로 실제 NPU처럼 병렬 MAC을 수행하지는 않음 |

### 시간 복잡도 분석

`mac_operation()` 함수는 입력 패턴과 필터의 모든 칸을 한 번씩 방문한다.
배열의 크기가 N x N이면 바깥 반복문은 N번 실행되고, 안쪽 반복문도 각 행마다 N번 실행된다.
따라서 전체 반복 횟수는 `N * N`이고, MAC 연산 횟수는 `N^2`이다.
각 반복에서는 곱셈 한 번과 덧셈 한 번이 수행되며, 이 작업은 배열 크기와 무관하게 일정한 시간에 가까운 기본 연산으로 볼 수 있다.
그래서 전체 시간 복잡도는 반복 횟수에 의해 결정되며 `O(N^2)`가 된다.
성능 측정 표에서도 크기가 커질수록 MAC 횟수가 9, 25, 169, 625로 증가하는 것을 확인할 수 있다.
실행 시간도 작은 측정 오차는 있지만 13x13과 25x25 구간에서 크기 증가에 따라 함께 증가한다.
3x3이나 5x5처럼 매우 작은 입력에서는 함수 호출 비용, 반복문 진입 비용, `perf_counter()` 측정 오차가 실제 계산 시간보다 크게 보일 수 있다.
그래서 작은 크기끼리는 MAC 횟수와 실행 시간이 정확히 비례하지 않을 수 있다.
하지만 N이 커질수록 측정 오차의 비중은 줄어들고, 모든 칸을 방문해야 하는 구조 때문에 실행 시간은 `N^2` 증가 경향에 가까워진다.
이 프로그램은 순수 Python 반복문으로 MAC을 순차 처리하므로 실제 NPU처럼 여러 MAC 유닛을 병렬로 사용하는 구조는 아니다.
따라서 현재 구현의 병목은 하드웨어 병렬 처리 부족과 Python 반복문 오버헤드에 있다.
보너스 기능의 1D flatten 방식은 인덱스 접근 단계를 줄여 상수 시간 비용을 줄일 수 있지만, 모든 원소를 한 번씩 처리한다는 점은 같으므로 복잡도 자체는 여전히 `O(N^2)`이다.

## 11. 보너스 기능

| 기능 | 설명 |
|---|---|
| Cross 생성 | `generate_cross(n)`으로 NxN Cross 패턴 생성 |
