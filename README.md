# E1-3_Multiply-ACcumulate
코디세이 입학연수과정 미션3 — Mini NPU Simulator (MAC 연산 시뮬레이터)

## 실행 방법

```
python main.py
```

실행하면 모드 선택 프롬프트가 나온다.

```
[모드 선택]
1. 사용자 입력 (3x3)
2. data.json 분석
선택:
```

- **1번 (사용자 입력)**: 3×3 필터 A/B, 3×3 패턴을 콘솔에서 직접 입력받아 MAC 점수·판정·연산 시간을 출력한다.
  - 필터 입력 단계에서 "직접 입력" 또는 "자동 생성(필터 A=Cross, 필터 B=X)" 중 하나를 고를 수 있다. 패턴은 판별 대상이므로 항상 직접 입력받는다.
- **2번 (data.json 분석)**: 실행 파일과 같은 폴더의 `data.json`을 읽어 5×5/13×13/25×25 케이스를 일괄 판정하고, PASS/FAIL과 성능 표를 출력한다.
- 두 모드 모두 종료 직전에 **보너스: 2D vs 1D 메모리 접근 최적화 비교**를 실행할지 y/n으로 묻는다. y를 선택하면 임의의 크기 N을 입력받아 2차원 배열 방식과 1차원(flatten) 방식의 MAC 연산 속도를 비교해 보여준다.

`data.json`은 `main.py`와 같은 디렉터리에 있어야 한다 (기본 경로: `./data.json`).

## 구현 요약

- **데이터 구조**: 패턴/필터는 `list[list[float]]` (2차원 리스트)로 저장한다. `matrix[i][j]`로 특정 위치 값을 바로 읽고 쓸 수 있다.
- **MAC 연산**(`mac_operation`): 이중 for문으로 `score += pattern[i][j] * filter[i][j]`를 누적한다. NumPy 등 외부 라이브러리는 사용하지 않는다.
- **라벨 정규화**(`normalize_label`): `filters`의 키(`cross`/`x`)와 `patterns`의 `expected` 값(`+`/`x`)을 하나의 함수로 표준 라벨 `Cross`/`X`로 통일한다. 표기가 서로 다른 두 출처(필터 키, expected 값)를 같은 규칙으로 정규화해야 "Cross 점수 5.0인데 expected가 '+'라서 문자열 비교가 실패하는" 식의 오류를 막을 수 있다.
- **판정/동점 처리**(`decide_winner`): `abs(score_a - score_b) < 1e-9`면 동점(모드1: `판정 불가`, 모드2: `UNDECIDED`)으로 처리하고, 그 외에는 점수가 더 높은 쪽을 승자로 판정한다. 부동소수점 연산은 수학적으로 같은 값이라도 계산 순서에 따라 마지막 비트가 달라질 수 있어(`0.9`가 `0.8999999999999999`로 나오는 식), `==` 비교 대신 허용오차(epsilon) 비교를 사용한다.
- **스키마 방어**: `data.json`의 각 패턴 케이스는 `evaluate_case` 함수 안에서 개별적으로 검증한다. 키 형식 오류, 필터 미존재, 크기 불일치, 라벨 정규화 실패 등 어떤 이유로도 예외를 밖으로 던지지 않고 그 케이스만 FAIL 처리한 뒤 다음 케이스로 넘어간다. 실제로 필터/패턴 크기가 어긋난 임의의 손상 JSON으로 테스트했을 때도 프로그램이 중단되지 않고 케이스 단위 FAIL만 출력하는 것을 확인했다.
- **보너스 1 (2D→1D 최적화)**: `flatten()`으로 2차원 리스트를 길이 N²의 1차원 리스트로 변환하고, `mac_operation_flat`은 이중 for문 대신 단일 for문(`pattern_flat[i] * filter_flat[i]`)으로 연산한다. 별도 메뉴가 아니라 모드 실행이 끝난 뒤 "실행할지" 묻는 형태로 붙여서 필수 흐름을 방해하지 않게 했다.
- **보너스 2 (패턴 생성기)**: `generate_cross(n)`/`generate_x(n)`이 임의의 홀수 크기 N에 대해 십자가/X 패턴을 생성한다. 모드 1의 필터 자동 생성 옵션과 보너스 1의 임의 크기 비교(예: 51×51)에서 재사용한다.

## 결과 리포트

### 콘솔 요약 (`data.json` 기준)

```
총 테스트: 6개
통과: 3개
실패: 3개

실패 케이스:
- size_5_1:  동점(UNDECIDED) 처리 규칙에 따라 실패
- size_13_2: 동점(UNDECIDED) 처리 규칙에 따라 실패
- size_25_1: 동점(UNDECIDED) 처리 규칙에 따라 실패
```

### 실패 원인 분석

3건의 FAIL은 전부 **"수치 비교 문제"** 범주이고, 데이터/스키마 문제나 판정 로직 자체의 버그는 아니다. 데이터/스키마 문제였다면 크기 불일치나 키 형식 오류 메시지가 찍혔을 것이고, 로직 문제였다면 정답이 뻔한 케이스(예: `size_5_2`, `size_25_2`)도 틀렸을 텐데 실제로는 그 케이스들은 모두 PASS했다.

- `size_5_1` (expected: X): Cross 점수 `0.9`, X 점수 `0.8999999999999999` → 두 값의 차이가 1e-9보다 작아 `UNDECIDED`로 판정, expected(X)와 달라 FAIL.
- `size_13_2` (expected: Cross): Cross 점수 `7.499999999999997`, X 점수 `7.5` → 역시 근소한 차이라 `UNDECIDED`.
- `size_25_1` (expected: X): Cross 점수 `4.9`, X 점수 `4.899999999999999` → 동일한 패턴.

세 케이스 모두 `data.json`의 필터 값 자체가 정수(1.0/0.0)가 아니라 `0.9`, `7.5`, `4.9`처럼 소수로 설계돼 있어서, MAC 연산(부동소수점 곱셈·덧셈의 누적)을 거치면 수학적으로는 같아야 할 값이 이진 부동소수점 표현의 반올림 오차 때문에 마지막 자리에서 미세하게 어긋난다. 이걸 `==`로 비교했다면 우연히 통과했을 수도, 실패했을 수도 있어 재현성이 없는데, `abs(a-b) < 1e-9` epsilon 정책을 적용하면 "사실상 같은 값"을 항상 동일하게 `UNDECIDED`로 취급하므로 일관된 결과가 나온다. 즉 이 FAIL들은 **버그가 아니라 epsilon 정책이 의도대로 동작한 결과**이며, `data.json` 제작자가 일부러 근접값을 넣어 이 상황을 재현하도록 설계한 것으로 보인다. 반대로 `size_5_2`, `size_13_1`, `size_25_2`처럼 두 점수 차이가 충분히 큰 케이스(예: `52.9` vs `0.1`)는 epsilon 범위를 훨씬 벗어나므로 안정적으로 PASS한다.

### 성능 표 해석과 O(N²) 근거

`mac_operation`은 필터 크기 n에 대해 `i`, `j` 각각 n번씩 이중 for문을 돌며 곱셈 1회 + 누적 덧셈 1회를 수행한다. 따라서 총 연산 횟수는 정확히 **N²**이고, 다른 모든 부분(비교, 라벨 정규화, 입출력)은 이 반복 안에 포함되지 않으므로 시간 복잡도는 **O(N²)**이다.

측정 결과 예시(연산 함수 호출 구간만 측정, 10회 평균):

| 크기 | 연산 횟수(N²) | 평균 시간(ms) |
|---|---|---|
| 3×3 | 9 | 0.0023 |
| 5×5 | 25 | 0.0072 |
| 13×13 | 169 | 0.0209 |
| 25×25 | 625 | 0.0718 |

연산 횟수는 3×3 대비 25×25가 625/9 ≈ 69배로 늘어나고, 실측 시간도 3×3(0.0023ms) 대비 25×25(0.0718ms)가 약 31배로 같은 방향(N이 커질수록 시간도 커짐)으로 증가한다. 정확히 69배가 아니라 31배인 이유는, 이 정도로 작은 N에서는 파이썬 인터프리터의 함수 호출/루프 진입 오버헤드와 `time.perf_counter()` 측정 자체의 잡음이 실제 곱셈·덧셈 연산 시간과 비슷한 크기여서 순수 N² 비율로 정확히 스케일링되지 않기 때문이다(반복 횟수를 늘리거나 N을 더 크게 하면 오버헤드 비중이 줄어들어 N²에 더 가깝게 수렴한다). 그럼에도 "N이 커질수록 시간이 단조 증가"하고 "5×5→25×25 구간(연산 횟수 25배)에서 시간도 대략 10배 이상 증가"하는 경향은 뚜렷하게 나타나, 반복문 기반 MAC 연산이 O(N²)이라는 근거를 실측으로도 뒷받침한다. 보너스1의 2D vs 1D 비교(예: 25×25에서 1D가 2D 대비 약 20~25% 빠름)는 두 방식 모두 여전히 O(N²)이지만, 2차원 리스트 인덱싱(`matrix[i][j]`, 바깥 리스트 참조 후 안쪽 리스트 참조)보다 1차원 인덱싱(`flat[i]`, 참조 1회) 쪽이 상수 계수가 더 작다는 것을 보여준다.

### 재현성 확인

- 모드 1: 문제 예시와 동일하게 필터 A=Cross, 필터 B=X, 패턴=X를 입력하면 `A 점수: 1.0`, `B 점수: 5.0`, `판정: B`가 그대로 출력됨을 확인했다.
- 모드 2: `data.json` 실행 시 `총 테스트: 6개 / 통과: 3개 / 실패: 3개`가 실패 케이스 목록(3건)의 개수와 일치함을 확인했다.
- 의도적 오류 입력: 모드 1에서 열 개수가 틀리거나 숫자가 아닌 값을 입력하면 `입력 형식 오류: ...` 메시지 후 해당 줄만 재입력을 받는다. 모드 2는 필터/패턴 크기를 인위적으로 틀어지게 만든 JSON으로 실행해도 프로그램이 중단되지 않고 해당 케이스만 FAIL 처리한 뒤 나머지 케이스와 성능 분석·요약까지 정상 출력됨을 확인했다.
