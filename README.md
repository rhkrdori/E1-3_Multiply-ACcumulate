# E1-3_Multiply-ACcumulate
코디세이 입학연수과정 미션3 — Mini NPU Simulator (MAC 연산 시뮬레이터)

## 실행 방법

```
python main.py
```

실행하면 모드 선택 프롬프트가 나온다.

```
[모드 선택]
1. 사용자 입력 (3x3)
2. data.json 분석
선택:
```

- **1번 (사용자 입력)**: 3×3 필터 A/B, 3×3 패턴을 콘솔에서 직접 입력받아 MAC 점수·판정·연산 시간을 출력한다.
  - 필터 입력 단계에서 "직접 입력" 또는 "자동 생성(필터 A=Cross, 필터 B=X)" 중 하나를 고를 수 있다. 패턴은 판별 대상이므로 항상 직접 입력받는다.
- **2번 (data.json 분석)**: 실행 파일과 같은 폴더의 `data.json`을 읽어 5×5/13×13/25×25 케이스를 일괄 판정하고, PASS/FAIL과 성능 표를 출력한다.
- 두 모드 모두 종료 직전에 **보너스: 2D vs 1D 메모리 접근 최적화 비교**를 실행할지 y/n으로 묻는다. y를 선택하면 임의의 크기 N을 입력받아 2차원 배열 방식과 1차원(flatten) 방식의 MAC 연산 속도를 비교해 보여준다.

`data.json`은 `main.py`와 같은 디렉터리에 있어야 한다 (기본 경로: `./data.json`).

## 구현 요약

- **데이터 구조**: 패턴/필터는 `list[list[float]]` (2차원 리스트)로 저장한다. `matrix[i][j]`로 특정 위치 값을 바로 읽고 쓸 수 있다.
- **MAC 연산**(`mac_operation`): 이중 for문으로 `score += pattern[i][j] * filter[i][j]`를 누적한다. NumPy 등 외부 라이브러리는 사용하지 않는다.
- **라벨 정규화**(`normalize_label`): `filters`의 키(`cross`/`x`)와 `patterns`의 `expected` 값(`+`/`x`)을 하나의 함수로 표준 라벨 `Cross`/`X`로 통일한다. 표기가 서로 다른 두 출처(필터 키, expected 값)를 같은 규칙으로 정규화해야 "Cross 점수 5.0인데 expected가 '+'라서 문자열 비교가 실패하는" 식의 오류를 막을 수 있다. `filters` 키는 `load_filters`에서 로드 시점에 정규화하고, `expected` 값은 `evaluate_case` 안에서 `decide_winner`로 점수를 판정하기 **직전**에 정규화한다(정규화 → 판정 → `verdict == expected` 비교 순서를 코드 순서와 일치시켰다). 다만 `decide_winner`는 두 점수(`score_cross`, `score_x`)만으로 승자를 정하고 `expected` 값을 전혀 참조하지 않으므로, `expected` 정규화 시점 자체가 판정 결과에 영향을 주지는 않는다 — 순서를 맞춘 것은 어디까지나 코드 가독성과 "정규화되지 않은 원본 문자열이 판정 로직에 섞여 들어가지 않는다"는 정합성을 보이기 위함이다.
- **판정/동점 처리**(`decide_winner`): `abs(score_a - score_b) < 1e-9`면 동점(모드1: `판정 불가`, 모드2: `UNDECIDED`)으로 처리하고, 그 외에는 점수가 더 높은 쪽을 승자로 판정한다. 부동소수점 연산은 수학적으로 같은 값이라도 계산 순서에 따라 마지막 비트가 달라질 수 있어(`0.9`가 `0.8999999999999999`로 나오는 식), `==` 비교 대신 허용오차(epsilon) 비교를 사용한다. 판정 로직 자체(점수 비교, epsilon 기준)는 모드1/모드2가 완전히 동일한 `decide_winner` 함수를 공유하며, 동점일 때 출력할 라벨 문자열만 `undecided_label` 인자로 갈라 넣는다. 두 모드의 동점 라벨을 일부러 다르게 준 이유는 각 모드의 사용 목적이 다르기 때문이다.
  - **모드1(`판정 불가`)**: 사람이 콘솔에서 즉석으로 입력하고 바로 읽는 대화형 UX다. 필터 라벨이 `A`/`B`처럼 사용자가 그 자리에서 붙인 임시 이름이므로, 결과도 자연스러운 한국어 문장(`판정: 판정 불가 (|A-B| < 1e-9)`)으로 보여주는 것이 가독성 면에서 낫다.
  - **모드2(`UNDECIDED`)**: `data.json`의 `expected` 필드가 `Cross`/`X`(정규화 후 영문 라벨)로 고정된 스펙이고, `evaluate_case`는 `verdict == expected` 문자열 비교로 PASS/FAIL을 기계적으로 판정한다. 이때 `expected`가 절대 가질 수 없는 예약값이 필요한데, 기존 라벨(`Cross`/`X`)과 표기 체계를 맞추기 위해 영문 상수 `UNDECIDED`를 그대로 사용했다. 즉 모드2의 동점 라벨은 사람이 읽는 문구가 아니라 "expected와 절대 일치하지 않는 판정 상태값"이라는 역할이 우선이라 한국어 문구 대신 영문 토큰을 쓴다.
- **스키마 방어**: `data.json`의 각 패턴 케이스는 `evaluate_case` 함수 안에서 개별적으로 검증한다. 키 형식 오류, 필터 미존재, 크기 불일치, 라벨 정규화 실패 등 어떤 이유로도 예외를 밖으로 던지지 않고 그 케이스만 FAIL 처리한 뒤 다음 케이스로 넘어간다. 실제로 필터/패턴 크기가 어긋난 임의의 손상 JSON으로 테스트했을 때도 프로그램이 중단되지 않고 케이스 단위 FAIL만 출력하는 것을 확인했다.
- **보너스 1 (2D→1D 최적화)**: `flatten()`으로 2차원 리스트를 길이 N²의 1차원 리스트로 변환하고, `mac_operation_flat`은 이중 for문 대신 단일 for문(`pattern_flat[i] * filter_flat[i]`)으로 연산한다. 별도 메뉴가 아니라 모드 실행이 끝난 뒤 "실행할지" 묻는 형태로 붙여서 필수 흐름을 방해하지 않게 했다.
- **보너스 2 (패턴 생성기)**: `generate_cross(n)`/`generate_x(n)`이 임의의 홀수 크기 N에 대해 십자가/X 패턴을 생성한다. 모드 1의 필터 자동 생성 옵션과 보너스 1의 임의 크기 비교(예: 51×51)에서 재사용한다.

## 결과 리포트

### 콘솔 요약 (`data.json` 기준)

```
총 테스트: 6개
통과: 3개
실패: 3개

실패 케이스:
- size_5_1:  동점(UNDECIDED) 처리 규칙에 따라 실패
- size_13_2: 동점(UNDECIDED) 처리 규칙에 따라 실패
- size_25_1: 동점(UNDECIDED) 처리 규칙에 따라 실패
```

### 실패 원인 분석

3건의 FAIL은 전부 **"수치 비교 문제"** 범주이고, 데이터/스키마 문제나 판정 로직 자체의 버그는 아니다. 데이터/스키마 문제였다면 크기 불일치나 키 형식 오류 메시지가 찍혔을 것이고, 로직 문제였다면 정답이 뻔한 케이스(예: `size_5_2`, `size_25_2`)도 틀렸을 텐데 실제로는 그 케이스들은 모두 PASS했다.

- `size_5_1` (expected: X): Cross 점수 `0.9`, X 점수 `0.8999999999999999` → 두 값의 차이가 1e-9보다 작아 `UNDECIDED`로 판정, expected(X)와 달라 FAIL.
- `size_13_2` (expected: Cross): Cross 점수 `7.499999999999997`, X 점수 `7.5` → 역시 근소한 차이라 `UNDECIDED`.
- `size_25_1` (expected: X): Cross 점수 `4.9`, X 점수 `4.899999999999999` → 동일한 패턴.

세 케이스 모두 `data.json`의 필터 값 자체가 정수(1.0/0.0)가 아니라 `0.9`, `7.5`, `4.9`처럼 소수로 설계돼 있어서, MAC 연산(부동소수점 곱셈·덧셈의 누적)을 거치면 수학적으로는 같아야 할 값이 이진 부동소수점 표현의 반올림 오차 때문에 마지막 자리에서 미세하게 어긋난다. 이걸 `==`로 비교했다면 우연히 통과했을 수도, 실패했을 수도 있어 재현성이 없는데, `abs(a-b) < 1e-9` epsilon 정책을 적용하면 "사실상 같은 값"을 항상 동일하게 `UNDECIDED`로 취급하므로 일관된 결과가 나온다. 즉 이 FAIL들은 **버그가 아니라 epsilon 정책이 의도대로 동작한 결과**이며, `data.json` 제작자가 일부러 근접값을 넣어 이 상황을 재현하도록 설계한 것으로 보인다. 반대로 `size_5_2`, `size_13_1`, `size_25_2`처럼 두 점수 차이가 충분히 큰 케이스(예: `52.9` vs `0.1`)는 epsilon 범위를 훨씬 벗어나므로 안정적으로 PASS한다.

### 성능 표 해석과 O(N²) 근거

`mac_operation`은 필터 크기 n에 대해 `i`, `j` 각각 n번씩 이중 for문을 돌며 곱셈 1회 + 누적 덧셈 1회를 수행한다. 따라서 총 연산 횟수는 정확히 **N²**이고, 다른 모든 부분(비교, 라벨 정규화, 입출력)은 이 반복 안에 포함되지 않으므로 시간 복잡도는 **O(N²)**이다.

측정 결과 예시(연산 함수 호출 구간만 측정, 10회 평균):

| 크기 | 연산 횟수(N²) | 평균 시간(ms) |
|---|---|---|
| 3×3 | 9 | 0.0023 |
| 5×5 | 25 | 0.0072 |
| 13×13 | 169 | 0.0209 |
| 25×25 | 625 | 0.0718 |

연산 횟수는 3×3 대비 25×25가 625/9 ≈ 69배로 늘어나고, 실측 시간도 3×3(0.0023ms) 대비 25×25(0.0718ms)가 약 31배로 같은 방향(N이 커질수록 시간도 커짐)으로 증가한다. 정확히 69배가 아니라 31배인 이유는, 이 정도로 작은 N에서는 파이썬 인터프리터의 함수 호출/루프 진입 오버헤드와 `time.perf_counter()` 측정 자체의 잡음이 실제 곱셈·덧셈 연산 시간과 비슷한 크기여서 순수 N² 비율로 정확히 스케일링되지 않기 때문이다(반복 횟수를 늘리거나 N을 더 크게 하면 오버헤드 비중이 줄어들어 N²에 더 가깝게 수렴한다). 그럼에도 "N이 커질수록 시간이 단조 증가"하고 "5×5→25×25 구간(연산 횟수 25배)에서 시간도 대략 10배 이상 증가"하는 경향은 뚜렷하게 나타나, 반복문 기반 MAC 연산이 O(N²)이라는 근거를 실측으로도 뒷받침한다. 보너스1의 2D vs 1D 비교(예: 25×25에서 1D가 2D 대비 약 20~25% 빠름)는 두 방식 모두 여전히 O(N²)이지만, 2차원 리스트 인덱싱(`matrix[i][j]`, 바깥 리스트 참조 후 안쪽 리스트 참조)보다 1차원 인덱싱(`flat[i]`, 참조 1회) 쪽이 상수 계수가 더 작다는 것을 보여준다.

### 대규모 연산(N≥1000)에서의 시간·메모리 제약과 최적화 우선순위

이 프로그램은 순수 파이썬 이중 for문(`mac_operation`)으로 MAC을 구현하므로, N이 커질수록 다음 두 자원이 함께 문제가 된다.

- **시간**: 반복 횟수는 정확히 N²이고, 파이썬 인터프리터는 각 반복마다 바이트코드 디스패치·리스트 인덱싱(`pattern[i][j]`, `filter_[i][j]` — 바깥 리스트 조회 후 안쪽 리스트 조회로 실질적으로 인덱싱 4회)·float 박싱 객체 생성/해제 오버헤드를 수반한다. N=1000이면 N²=1,000,000회 반복이라, 컴파일된 코드(C/NumPy)라면 수 ms면 끝날 연산이 순수 파이썬에서는 (환경에 따라 다르지만) 수백 ms~수 초까지 늘어날 수 있고, `REPEAT_COUNT=10`으로 평균을 내는 현재 구조에서는 측정 한 번에 이 값이 10배로 누적된다.
- **메모리**: 파이썬의 `float`는 C의 `double`처럼 8바이트로 압축 저장되지 않고 개별 객체(오버헤드 약 24~28바이트)로 힙에 존재하며, 리스트도 각 원소에 대한 포인터(8바이트)를 따로 든다. N×N 행렬 하나가 이미 원소 개수(N²) × (포인터 8B + float 객체 ~28B)에 가까운 메모리를 쓰고, 필터 A/B와 패턴까지 합치면 N=1000 기준 수십~수백 MB 단위로 커질 수 있다. 보너스1의 `flatten()`은 원본 2차원 리스트를 유지한 채 별도의 1차원 리스트를 새로 만들기 때문에, 큰 N에서는 그 순간 원본+flat 사본이 동시에 메모리에 존재해 피크 메모리 사용량이 일시적으로 커진다.

우선적으로 고려할 최적화 항목(현재 구현은 "외부 라이브러리 미사용" 제약 안에서 반복문 기반 MAC의 동작 원리를 보이는 것이 목적이라 아래는 적용하지 않고 방향만 남긴다):

1. **이중 인덱싱 제거**: 안쪽 루프 진입 전에 `row_p = pattern[i]`, `row_f = filter_[i]`로 행을 한 번만 참조해두면, 안쪽 루프에서 `row_p[j] * row_f[j]`로 인덱싱 횟수를 절반으로 줄일 수 있다(보너스1의 2D→1D 개선과 같은 방향의 최적화).
2. **블록화(타일링)**: N이 매우 커지면(캐시 크기를 넘어서면) 행렬을 작은 블록 단위로 나눠 블록 내부에서 연산을 끝내고 다음 블록으로 넘어가는 방식이 캐시 적중률을 높인다. 파이썬 리스트는 원소가 메모리에 연속으로 배치되지 않아(포인터의 배열이라) 블록화 효과가 NumPy 배열만큼 크지는 않지만, 대규모 N에서 다음 최적화 단계로 고려할 항목이다.
3. **벡터화(NumPy 등)**: 가장 큰 폭의 개선이지만 이 과제의 "외부 라이브러리 미사용" 요구사항과 배치돼 이번 구현에는 적용하지 않았다. 실무에서 N=1000 이상을 다뤄야 한다면 최우선 순위다.
4. **병렬화(멀티프로세싱)**: CPU 코어 여러 개에 행 구간을 나눠 분배할 수 있다. 다만 파이썬 GIL 때문에 스레드로는 CPU-bound 반복문의 실질적 병렬화가 안 되고, 멀티프로세싱은 프로세스 간 데이터(행렬) 복사/직렬화 비용이 커서 N이 충분히 크지 않으면 오히려 손해다. N≥1000 규모부터 도입을 검토할 만하다.
5. **메모리 사용량 축소**: `flatten()`처럼 원본을 유지한 채 사본을 새로 만드는 대신, 필요한 시점에만 스트리밍하듯 값을 소비하거나(제너레이터), 애초에 2차원 대신 1차원 리스트 하나로만 데이터를 유지해 사본 자체를 만들지 않는 방향이 대규모 N에서는 더 안전하다.

### CPU(직렬) vs NPU(병렬)의 병목 차이

이 시뮬레이터의 `mac_operation`이 실제로 흉내 내는 것은 "CPU 한 코어가 MAC 연산을 어떻게 처리하는가"이고, 이름은 NPU 시뮬레이터지만 구현 자체는 진짜 NPU의 병렬 하드웨어를 흉내 내지는 않는다. 이 차이를 명확히 하면:

- **CPU(이 프로그램의 동작 방식)**: N² 개의 곱셈-누적을 단일 실행 흐름(싱글 스레드)에서 하나씩 순서대로 처리한다. 병목은 "연산 개수 × (연산당 처리 시간)"으로, 처리 시간에는 실제 곱셈·덧셈보다 파이썬 인터프리터의 반복문/함수 호출 오버헤드와 메모리 접근(리스트 인덱싱, 캐시 미스) 지연이 더 크게 기여한다. 즉 **명령(연산) 개수에 비례해 시간이 늘어나는 직렬(serial) 병목**이다.
- **NPU(실제 하드웨어)**: 다수의 MAC 유닛(예: systolic array)이 한 사이클에 여러 원소쌍을 동시에 곱하고 누적한다. 이 경우 병목은 더 이상 "연산 개수"가 아니라 **그 많은 MAC 유닛에 데이터를 얼마나 빨리 공급할 수 있는가(메모리 대역폭)**로 옮겨간다. 연산 유닛 수를 아무리 늘려도 가중치/입력을 유닛에 채워 넣는 속도가 못 따라가면 유닛들이 놀게 되므로(compute-bound가 아니라 memory-bandwidth-bound), 실제 NPU 설계는 온칩 버퍼·데이터 재사용 전략(weight-stationary 등)으로 이 병목을 완화하는 데 집중한다.
- **이 프로그램의 한계**: 보너스1(2D→1D)은 인덱싱 오버헤드를 줄여 "메모리 접근 방식이 성능에 영향을 준다"는 것을 보여주지만, 여전히 파이썬 한 코어에서 N² 회를 순서대로 실행하는 **직렬(CPU형) 병목** 안에서의 상수 계수 개선일 뿐이다. 진짜 NPU처럼 연산을 공간적으로 병렬화(P개의 MAC 유닛으로 시간을 O(N²/P)에 가깝게 줄이는 것)하려면 외부 병렬 연산 라이브러리나 실제 병렬 하드웨어가 필요하며, 이는 이번 과제의 "외부 라이브러리 미사용, 반복문 직접 구현" 요구사항 범위를 벗어난다.
